# Law Agent 체크리스트 선택 및 실행 구조

## 1. 전체 개요

Law Agent는 사전에 정의된 법률 질문 체크리스트를 기반으로 폐기물 사례에 필요한 법률 판단을 수행한다.

체크리스트를 LLM이 매번 새롭게 생성하는 방식이 아니라, **고정된 질문 목록을 불러온 후 입력 사례의 특성에 따라 하위 질문을 추가하고, 선행 질문의 판단 결과에 따라 실행할 질문을 결정하는 구조**이다.

전체 처리 과정은 다음과 같다.

```text
파트 1: 폐기물 사례 입력
        |
        v
    Planner
        |
        v
  checklist.yaml 로드
        |
        v
  혼합 폐기물 여부 확인
        |
        +----------------------+
        |                      |
     단일 성분               복수 성분
        |                      |
   기본 질문 유지        성분별 하위 질문 생성
        |                      |
        +----------+-----------+
                   |
                   v
          최종 질문 목록 생성
                   |
                   v
                Schedule
                   |
                   v
               Retriever
                   |
                   v
                Evidence
                   |
                   v
                 Judge
                   |
                   v
               Verifier
                   |
                   v
           다음 질문 실행 여부 확인
                   |
          +--------+--------+
          |                 |
       실행할 질문 있음    판단 종료
          |                 |
          v                 v
       다음 라운드        Composer
```

## 2. 1단계: 기본 체크리스트 로드

Planner는 `config/checklist.yaml`에 정의된 질문 목록을 불러온다.

기본 체크리스트는 총 10개 분야로 구성되며, 폐기물의 분류부터 재활용 가능 여부, 처분, 위탁, 신고 및 처리업체 자격까지 확인한다.

| 분야 | 주요 확인 내용 |
|---|---|
| A. 폐기물 분류 | 분류번호, 지정폐기물 여부, 혼합 여부 |
| B. 재활용 금지·제한 | 재활용 금지 및 제한 여부 |
| C. 순환자원 지정 여부 | 순환자원 지정 품목 및 지정 기준 |
| D. 재활용 가능 여부 | 허용 R코드, 재활용 기준 및 준수사항 |
| E. 에너지 회수 | 에너지 회수 인정 기준 |
| F. 폐기물 처분 | 허용 처분 방법 및 조건 |
| G. 위탁 및 서류 | 위탁 절차, 올바로, 운반 기준 |
| H. 신고 및 처리계획 | 배출자 신고 및 처리계획 확인 |
| I. 처리업체 자격 | 처리업 및 운반업체 자격 |
| J. 품목별 특별법 | 전기전자제품, 건설폐기물 등 특별법 |

기본 질문은 Planner에서 임의로 삭제하지 않는다.

체크리스트 경로는 다음과 같이 결정된다.

1. `LAW_AGENT_CHECKLIST` 환경변수가 설정되어 있으면 해당 경로 사용
2. 설정되어 있지 않으면 `config/checklist.yaml` 사용

## 3. 2단계: 혼합 폐기물에 따른 하위 질문 생성

Planner는 입력 사례의 `components` 정보를 확인한다.

- 성분이 1개 이하인 경우: 기본 질문만 사용
- 성분이 2개 이상인 경우: 지정된 부모 질문에 성분별 하위 질문 추가

현재 성분별 분리가 적용되는 질문은 6개이다.

```python
SPLIT_PARENTS = (
    "A-1",
    "A-2",
    "B-1",
    "B-2",
    "D-1",
    "F-1"
)
```

### 3.1 성분별 질문을 추가하는 이유

혼합 폐기물은 성분에 따라 폐기물 분류, 지정폐기물 해당 여부, 재활용 가능 여부 및 처분 방법이 달라질 수 있다.

따라서 혼합 폐기물 전체에 하나의 질문만 적용하는 대신, 해당 질문을 성분별로 나누어 검토한다.

### 3.2 하위 질문 생성 예시

입력 사례:

```json
{
  "components": [
    {
      "material": "알루미늄",
      "share_pct": 60
    },
    {
      "material": "구리",
      "share_pct": 40
    }
  ]
}
```

D-1 질문을 기준으로 보면 다음과 같이 생성된다.

| 질문 ID | 질문 내용 |
|---|---|
| D-1 | 이 분류번호에 허용된 재활용 유형은 무엇인가? |
| D-1.c1 | 알루미늄 성분에 허용된 재활용 유형은 무엇인가? |
| D-1.c2 | 구리 성분에 허용된 재활용 유형은 무엇인가? |

하위 질문 ID는 다음 규칙을 사용한다.

```text
부모 질문 ID + .c + 성분 번호
```

예시:
- A-1.c1
- A-1.c2
- D-1.c1
- D-1.c2

### 3.3 부모 질문의 속성 상속

하위 질문은 부모 질문의 판단 설정을 그대로 상속한다.

| 속성 | 역할 |
|---|---|
| `stage` | 질문 단계 |
| `answer_type` | 답변 유형 |
| `min_laws` | 최소 법령 근거 |
| `needs_facts` | 판단에 필요한 사실 |
| `when` | 질문 실행 조건 |
| `feeds` | 선행·후속 질문 연결 |
| `search` | 검색 설정 |
| `baseline` | 기본 판단 설정 |

따라서 하위 질문은 부모 질문의 법률적 판단 기준과 실행 조건을 유지하면서 성분별로 독립적인 검토를 수행할 수 있도록 만들어진다.

## 4. 3단계: 조건부 질문 실행

Planner는 모든 질문을 생성하지만, 모든 질문을 즉시 실행하지는 않는다.

질문에 정의된 `when` 조건을 Planner가 직접 평가하지 않고 그대로 보존한다.

이후 Schedule과 Verifier가 앞선 질문의 답변을 기반으로 실행 가능 여부를 판단하는 구조이다.

### 4.1 조건부 질문 예시

A-3 질문:

> 지정폐기물 여부를 위탁 전에 분석·확인해야 하는 대상인가?

실행 조건:

```text
A-2가 '예'가 아닌 경우
```

질문 실행 흐름:

```text
A-2. 지정폐기물인가?
        |
        +-------------------+
        |                   |
       예                아니오 / 분석해야 앎
        |                   |
    A-3 실행 조건         A-3 실행
    충족하지 않음
```

즉, A-2의 판단 결과에 따라 A-3의 실행 여부가 결정된다.

### 4.2 조건부 질문의 역할

조건부 질문을 사용하는 목적은 다음과 같다.

1. 앞선 판단과 관계없는 질문의 불필요한 실행 방지
2. 법률 판단의 선후 관계 유지
3. 필요한 정보가 확보된 이후 후속 질문 실행
4. 질문 간 의존성 관리

주의할 점은 현재 확인된 Planner 코드에서는 `when`을 해석하지 않는다는 것이다. 실제 조건 평가 규칙은 Schedule 구현을 확인해야 한다.

## 5. 4단계: 질문 실행 순서 결정

Planner가 최종 질문 목록을 생성하면 판단 루프가 시작된다.

`loop.py`에서는 다음 순서로 실행한다.

```python
for r in range(1, MAX_ROUNDS + 1):

    ready = ready_ids(st)

    if not ready:
        break

    apply(st, retriever.node(st))
    apply(st, evidence.node(st))
    apply(st, judge.node(st, jcfg))
    apply(st, verifier.node(st, vcfg))
```

### 5.1 실행 모듈별 역할

| 순서 | 모듈 | 주요 역할 |
|---|---|---|
| 1 | Planner | 체크리스트 생성 및 하위 질문 추가 |
| 2 | Schedule | 현재 실행 가능한 질문 확인 |
| 3 | Retriever | 관련 법령 및 자료 검색 |
| 4 | Evidence | 판단에 필요한 근거 구성 |
| 5 | Judge | 법률적 판단 수행 |
| 6 | Verifier | 판단 결과 검증 |

### 5.2 반복 실행 구조

각 라운드가 끝나면 Verifier의 판단 결과를 반영하고 다음 라운드에서 실행할 질문을 다시 확인한다.

```text
Round 1
  질문 실행
  Retriever → Evidence → Judge → Verifier
                  |
                  v
Round 2
  실행 가능한 질문 재확인
  Retriever → Evidence → Judge → Verifier
                  |
                  v
Round 3
  실행 가능한 질문 재확인
                  |
                  v
             판단 종료
```

실행할 질문이 없거나 Verifier가 Composer로 이동하도록 판단하면 루프를 종료한다.

## 6. 5단계: 특정 질문만 실행하는 기능

현재 `loop.py`에는 `only` 옵션이 존재한다.

```python
if only:
    st["questions"] = [
        q for q in st["questions"]
        if q.base_id in only
    ]
```

이 기능은 전체 체크리스트 대신 지정한 질문만 실행할 때 사용한다.

예를 들어 다음과 같이 지정할 수 있다.

```python
only = ["A-1", "A-2", "D-1"]
```

그러면 해당 부모 질문과 부모 ID를 공유하는 성분별 하위 질문도 함께 필터링된다.

이 기능은 특정 법률 분야만 테스트하거나 개별 질문의 판단 결과를 검증할 때 활용할 수 있다.

## 7. 실행 기록 및 감사 로그

Planner와 각 실행 모듈은 Audit 정보를 기록한다.

Planner의 경우 다음 정보를 남긴다.

```python
{
    "node": "planner",
    "summary": {
        "checklist": 30,
        "sub_questions": 12,
        "components": 2,
        "notes": []
    },
    "output": {
        "question_ids": [
            "A-1",
            "A-1.c1",
            "A-1.c2"
        ]
    }
}
```

위 값은 구조 설명을 위한 예시이다.

주요 기록 항목은 다음과 같다.

| 항목 | 설명 |
|---|---|
| `checklist` | 기본 체크리스트 질문 수 |
| `sub_questions` | 추가 생성된 하위 질문 수 |
| `components` | 입력 사례의 성분 수 |
| `question_ids` | 최종 생성된 질문 ID |
| `audit` | 모듈별 실행 및 판단 기록 |
| `errors` | 실행 중 발생한 오류 |

이를 통해 어떤 질문이 생성되었고, 각 모듈에서 어떤 순서로 처리되었는지 추적할 수 있다.

## 8. 현재 구현의 핵심 특징 및 한계

| 구분 | 구현 방식 |
|---|---|
| 기본 질문 생성 | YAML 기반 고정 체크리스트 |
| 질문 추가 | 혼합 폐기물의 성분 수에 따라 추가 |
| 성분별 분리 | 6개 부모 질문에 적용 |
| 조건부 실행 | `when`을 보존하고 Schedule에 위임 |
| 질문 실행 순서 | Schedule 기반 |
| 법률 판단 | Retriever → Evidence → Judge → Verifier |
| 질문 자동 생성 | LLM 기반 생성 기능 미구현 |
| 실행 추적 | Audit 기록 |

### 핵심 정리

현재 Law Agent는 다음 세 가지 원리를 기반으로 동작한다.

1. **고정형 체크리스트:** 법률적으로 검토해야 할 기본 질문을 사전에 정의한다.
2. **사례 기반 질문 확장:** 혼합 폐기물인 경우 지정된 질문을 성분별 하위 질문으로 확장한다.
3. **조건부 순차 실행:** 앞선 질문의 판단 결과에 따라 Schedule이 후속 질문의 실행 가능 여부를 관리한다.

따라서 전체 구조는 **고정형 법률 질문 목록 + 혼합 성분별 질문 확장 + 선행 판단 기반 조건부 실행** 방식으로 정리할 수 있다.

## 9. 추가로 확인해야 할 구현 파일

현재 확인된 `planner.py`와 `loop.py`만으로는 조건부 실행의 내부 규칙까지 완전히 확인할 수 없다.

다음 파일을 함께 확인해야 전체 질문 선택 알고리즘을 파악할 수 있다.

| 파일 | 확인할 내용 |
|---|---|
| `config/checklist.yaml` | 질문별 `when`, `feeds`, `needs_facts` |
| `agents/schedule.py` | 질문 활성화 및 실행 순서 결정 |
| `state.py` | 질문 객체, 답변 상태, 하위 질문 ID 및 상태 관리 |
| `agents/verifier.py` | 판단 결과 검증 및 재실행·종료 결정 |

이 파일들을 함께 분석하면 체크리스트가 생성되는 시점부터 최종 법률 판단이 완료되는 시점까지 전체 데이터 흐름을 확인할 수 있다.
