# 설계도에 따른 순차 구현 계획

설계도 13쪽의 5개 묶음을 유지합니다. 여러 에이전트를 먼저 만들지 않고 단일 파트 1과 명시적 처리 흐름으로 시작합니다. 파트 2·3은 계약과 보완 요청 인터페이스까지만 연결하며 별도 설계 없이 해당 기능을 만들어 확정하지 않습니다.

## M1 — 계약 먼저: 개발 기준본 완료, 팀 합의 대기

- WasteCase·Fact·Evidence·InformationRequest·이벤트 계약 및 JSON Schema
- 합성 사례 3개, 원문·단위·확인 수준을 구분하는 테스트
- 자체 DOCX 읽기 전용 탐색기
- 다음 담당자가 검토할 문서: CONTRACT_DECISIONS.md
- 통과 기준: 로컬 자동 테스트 통과, 사례 구조 검증, 예시 양식 후보 0건

## M2 — 다음 작업: 최소 수직 흐름 완성

먼저 자체 DOCX **한 건**으로 다음을 연결합니다.

```text
임시 접수 → 파일 검사·해시 → 정형 추출 → 초안 저장
→ 보완 질문 1회 → 응답 저장·검증 → 사용자 검토 승인
→ 새 버전 JSON 발행 + outbox → 파트 2 계약 소비자
```

### 구현 순서

1. FastAPI 서비스와 PostgreSQL 마이그레이션. companies/sites/submissions를 분리.
2. 인증 주체와 company 범위 검사. 비공개 파일·작업·DB 모두 동일 테넌트 경계 적용.
3. 원본 저장·파일 제한·sha256·추출기 버전 캐시. idempotency_key 중복 접수 방지.
4. `POST /submissions`, `/submissions/{id}/files`, `/submissions/{id}/extract`, `GET /jobs/{id}`.
5. 파서 출력 후보 → 서버 검증 → fact_assertions/evidence/fact_evidence 저장. 원문 보존.
6. 질문 규칙 1개와 `POST /information-requests/{id}/answers`. answered와 resolved 분리.
7. `PATCH /cases/{id}/facts`에 base_revision·근거·사유. 경합은 409, 사용자 수정 보존.
8. 원문/추출값 비교와 승인 화면. UI·채팅 수정은 같은 API 사용.
9. `POST /cases/{id}/publish`: 검토 전·중대한 연결 충돌 거절, 불변 case_versions+outbox 원자 기록.
10. `GET /cases/{id}/versions/{version}` 및 파트 2 검증용 소비자. 실제 경로·업체 판정은 하지 않음.
11. 이후 다중 폐기물·다대다 근거·질문 중복 억제·수정 이력 확장.

### M2 통과 기준

- 합성 DOCX 작성값이 원문 근거와 함께 저장됨.
- 질문 1회→답변→승인→발행→파트 2 수신까지 실제 실행.
- 재업로드/중복 실행으로 건·이벤트 중복 없음.
- 승인 전 발행 거절, 다른 업체 자료 접근 거절, 동시 수정 409 확인.
- 건별 전체·근접 사진의 실제 첨부 여부를 검사. 부족하면 명시적인 제한/보완 상태.
- 화면을 제공하면 브라우저에서 한글 입력·저장·승인·화면 이동을 직접 검증.

## M3 — 추출 확대

PDF 텍스트+페이지/좌표, 스캔/OCR/layout, 분석서 시료·단위·검출한계 수집. 낮은 신뢰도의 수치·체크는 확인 요청. Azure 서비스는 도입 계정·데이터 처리 조건·요금 검토 후 연결하며 키를 코드에 넣지 않음. 읽기 실패 시 임시 접수 유지·대체 자료 요청·재시도/재개 구현.

## M4 — 분류 및 자료 안내

시연할 소수 폐기물군만 검수된 공식 법령 조건표로 지원. 원문/해시/개정·시행일/검수자 기록 후 활성화. 조건은 true/false/unknown, 범위 밖은 selected_code=null. 안내 카드는 필요 이유·공식 경로·검색어·준비정보·대안을 포함. URL을 생성하지 않고 검증 기록을 남김. 올바로 API는 사용하지 않음.

## M5 — 통합 검증

파트 2·3 요청→답변→재발행→후속 stale→재검토. event_id 중복 소비 차단. 개인정보/테넌트 경계, 동시 수정, 장애 재개, 버전별 원문 추적을 통합 테스트. 프롬프트 조정과 분리한 검증 세트로 필드·근거 위치 정확도/불필요 질문 수/처리시간/OCR·LLM 호출량 측정.

## 시작 시 필요한 운영 결정

M2 로컬 개발은 합성 자료로 시작할 수 있습니다. 외부 연결 전에만 DB/저장소 배포 환경, 로그인 방식, 운영 담당자, 보관·삭제 정책을 확정합니다. 실제 고객 자료·API 키·등록번호를 샘플 데이터에 넣지 않습니다.
