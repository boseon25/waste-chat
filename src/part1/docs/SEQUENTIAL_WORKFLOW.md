# 단계별 에이전트 구현 계획 및 현재 상태 — 0.2.4

## 목표 흐름

```text
1. 초기 입력서 작성 → 업로드·저장 → 원문/추출 후보/누락 확인 → 사용자 검토 기록
2. 필요한 추가 질문 선택 → 답변 저장·규칙 검증 → 정정·이력·건별 데이터 확인
3. 답변만으로 부족할 때 필요한 자료 제시 → 확보/신청 경로·준비자료 안내
   → 자료 수령 → 동일 건·현장·시료·시점 적용성 검토 → 필요 항목 반영
```

서류가 없어도 확인 가능한 정보는 먼저 사용합니다. 사진 2장도 실제 첨부가 있는지 별도로 확인해야 합니다. 자료 없음/모름은 허용하고 일괄 분석이나 모든 서류를 요구하지 않습니다. 본 제품은 재활용 경로 확정, 법적 판정, 행정 자동 제출을 하지 않습니다.

## 현재 구현 상태

| 단계 | 구현된 것 | 미구현/주의 |
|---|---|---|
| 1 작성·확인 | DOCX 빈 양식 복사, 사용자 작성 후 접수, SQLite 원본/추출값 저장, 재조회·무결성 대조, 건별 원문·후보·누락 비교, 명시적 입력 검토 기록 | 웹 입력/수정 UI, 진위 검증, 사진 실제 첨부·식별 검증, 컨트롤 밖 텍스트 완전 자동 해석 미구현 |
| 2 질문·저장 | 측정일 질문·답변·정정·이력·JSON 반영. 추가 자료 질문의 수동 생성·자유 텍스트/모름·정정·이력 저장 | 모든 필드별 답변의 타입/단위/시점/대상 검증·사실 반영과 질문 자동 우선순위 미구현 |
| 3 문서·경로 | 주제별 안내 카드, 담당자/기관 출발 경로, 준비정보, 대안, 첨부 BLOB 보관, 자료 없음/모름 기록 | 질문 답변에 기반한 필요 문서 자동 결정, 첨부 내용 추출·확인, 실제 신청서 초안/공식 서식 채우기, 접수기관별 상세 절차 검증 미구현 |
| 연결 | 기존 기능을 같은 CLI로 실행 가능 | 단계 전환 자동 강제는 아직 없음. 직접 순서대로 실행해야 함. 발행/파트2 실행도 미구현 |

본 버전의 initial-confirm은 검토자가 입력 내용과 누락을 살폈다는 **자기 기재 기록**입니다. 인증된 서명·법적 확정·자동 발행 승인도 아니며 fact의 verification이나 draft_revision을 변경하지 않습니다. JSON에서 해당 검토 기록을 내보내는 기능도 아직 없습니다. 정보가 없거나 불확실해도 이를 인정하고 기록할 수 있으나 해당 값이 자동 확정되지는 않습니다.

## 1단계 사용 방법

1. 양식을 새 파일로 복사합니다. 기존 파일은 덮어쓰지 않습니다.

```bash
python db_intake.py template --out output/my_intake.docx
```

2. Word에서 회색 예시를 지우고 실제 값을 작성합니다. 모르면 모름으로 기재하고, 체크는 각 항목별 하나만 선택합니다. 이 양식은 사용자가 제공한 기존 원본 그대로이며 폐기물 2에는 별도 현장 칸이 없습니다. 폐기물 2의 별도 현장이 필요하면 원문에 명확히 표시하되, 컨트롤 없는 임의 편집의 자동 해석은 보장하지 않으므로 검토 화면과 후속 질문으로 재확인해야 합니다. 추후 양식 개정이 필요합니다.
3. 저장한 DOCX를 DB에 접수합니다. 가상 예시에만 `--synthetic`을 사용합니다.

```bash
python db_intake.py ingest output/my_intake.docx --db output/intake.sqlite3
python db_intake.py inspect --db output/intake.sqlite3
python db_intake.py verify --db output/intake.sqlite3
```

4. inspect에서 폐기물 ID를 확인하고 각 건에 대해 원문 컨트롤과 원문 셀/문단, 추출 후보, 누락·제한을 비교합니다. 위치는 0부터 시작합니다.

```bash
python db_intake.py initial-preview --db output/intake.sqlite3 --case CASE_ID
```

5. 값과 제한을 읽은 사람만 화면에 출력된 검토 해시를 사용해 명시적으로 기록합니다.

```bash
python db_intake.py initial-confirm --db output/intake.sqlite3 --case CASE_ID --reviewer "검토자" --review-hash PREVIEW_HASH --acknowledge-limitations
python db_intake.py initial-history --db output/intake.sqlite3 --case CASE_ID
```

미확인·불일치가 있으면 이를 해소하지 않은 채 사실로 확정할 수 없습니다. 검토 확인 전 원본을 고쳐야 한다면 이 버전에는 초기 필드 수정 API가 없으므로 사용자가 DOCX를 수정해 새 제출로 다시 접수하고 검토해야 합니다. 해시가 달라지면 이전 표시 화면으로 확인할 수 없습니다. 초기 검토 기록은 다음 기능의 필수 게이트로 아직 강제하지 않습니다.

사진, 측정일, 유해물질 등 미확인은 보완 질문 단계에서 확인합니다. 개인·기업 자료가 들어간 SQLite는 로컬 개발 검증용이므로 공유 금지. `inspect`/`initial-preview` 출력에는 담당자 등 개인정보가 포함됩니다.

## 다음 구현 순서 및 완료 조건

### 2단계 — 추가 질문과 저장 검증

1. 선택 규칙: 대상 연결·충돌 → 분류를 바꾸는 정보 → 선택 경로/서식 필수 정보. 1회 1–3개 제시. 모든 항목을 일괄 요구하지 않음.
2. 건 ID·필드·목적별 응답 규칙(형식, 단위, 질량/부피 구분, 기간, 미확인, 근거)을 정의하고 수량·재질·유해성·월별 발생량을 단계별 추가.
3. 답변 저장→검증 결과→채택/보류를 분리. 기존 주장과 정정 이력 유지. 첨부는 업로드만으로 validated/resolved 금지.
4. 완료 테스트: 두 폐기물 각각 독립 저장, null/false/불검출 구분, 모호한 답변 재질문, ‘모름/자료 없음’ 재요구 억제, 수정 이력 보존, 필드 오류·충돌 시 조용한 덮어쓰기 금지. 기존 측정일 테스트와 회귀 테스트 모두 통과.

### 3단계 — 필요한 문서와 신청·확보 경로

1. 2단계 질문별로 답변만으로 충분한지/증빙이 필요한지/현재 판단이 보류되는지 구분. 사진이나 MSDS를 분석서로 대체 금지.
2. 사내 보관본 → 발급기관/관할 담당부서 → 필요 시 시험기관 문의 순으로 안내. 신청이 필요한 경우 **기관·민원 유형·현장 관할**을 확인한 뒤 신청 목적, 준비항목, 작성 예시, 공식 검색 출발점, 확인일과 재확인 필요 범위를 보여줌.
3. 공식 양식과 수신기관을 확인한 경우에만 검토용 신청 초안을 작성. 없는 값은 빈칸/미확인으로 유지. 작성 예시와 정식 신청서·기존 증명서를 구분. 실제 접수·전송은 사용자 확인 후 별도 절차.
4. 확보한 자료의 발급기관·문서일·현장·품목·시료·채취시점·공정 적용성을 확인하고, 불일치·미확인 자료는 보류. 결과를 공인 분석값이나 법적 분류로 자동 승격 금지.
5. 완료 테스트: 필요한 경우에만 카드/신청 지원, 기관·서식이 불확실할 때 확정 안내 금지, 안내 링크/검증일 표시, 제출 전 사용자 검토, 과거/타 현장 자료 자동 채택 0건, unavailable 이후 재질문 금지.

## 개발·운영 경계

0.2.4는 로컬 SQLite·CLI 데모입니다. 운영용 DB·인증/테넌트 접근권한·악성파일 검사·보관/삭제 정책·비공개 저장소·낙관적 잠금·서버·사용자 화면·불변 발행은 미구현입니다. 실제 업체 자료를 넣어 운영하기 전 별도로 설계·검증해야 합니다. 공식 링크는 현재 GUIDE 기록의 홈페이지 확인 범위일 뿐, 신청 가능성과 개별 민원을 보장하지 않습니다.
