초기 입력서 검토 · 보완 질문 · 자료 안내 · 다음 파트 전달 규격

설계 기준 2026.11.08 | 제안 계약 버전 2.0

결론: 입력서는 유지하고, 검증과 보완 절차를 강화한다

현재 입력서는 업체·발생 공정·이번 처리량·외형·혼합·오염·유해물질·사진을 폐기물별로 모으므로 초기 수집에 적합하
다. 다만 이 정보만으로 법적 분류, 재활용 가능성, 제출용 서류의 정확성이 완성되지는 않는다. 파트 1은 원문, 확인 수준,
적용 대상을 함께 전달해야 한다.

결정              설계 방향


입력 방식           문서 업로드 + 폐기물별 사진 연결 + 대화형 보완 + 추출 결과 확인 화면. 화면에서 수정한 값도 같은 데이터
                구조에 저장한다.


구현 방식           단일 에이전트와 정해진 처리 순서. 문서 파싱·단위 계산·검증·저장은 코드가 담당하고 LLM은 추출 보조와
                질문 표현에 사용한다.


분류의 범위          일상 명칭을 정규화하고 법령상 분류 후보와 부족한 근거를 제시한다. 재활용 경로 결정·업체 적격성·법적
                최종 검토는 다음 파트의 책임이다.


외부 연계           올바로 API를 사용하지 않는다. 기업별 원본 자료는 사용자가 제출한다. 공개 법령과 검증된 안내 링크를 별
                도 관리한다.


핵심 산출물          WasteCase 버전, 필드별 근거, 분류 후보, 충돌·누락 목록, 후속 질문, 단계별 사용 가능 범위.




정확성의 기준

JSON 형식이 맞는 것과 사실이 맞는 것은 다르다. 원문에 없는 값은 채우지 않고, 사용자의 답변과 시험 결과를 구분한다.
모든 자동 판정은 어떤 입력과 규칙을 사용했는지 되짚을 수 있어야 한다.

칸 추가 대신 화면과 파서에서 해결할 사항

사진·계량표·분석서는 업로드 화면에서 “어느 폐기물의 자료인지” 고르게 한다. 문서에 적힌 파일명만으로 첨부 완료 처
리하지 않는다. 전체·근접 각 1장 이상인지, 같은 사진을 두 번 올렸는지, 내용이 식별 가능한지 확인한다.

문서의 “예: …”가 남아 있는 칸은 실제 답변으로 저장하지 않는다. 예시만 있는 폐기물 2 표도 신규 건으로 만들지 않는다.
일부만 고친 표는 실제 건 후보로 보여주고 빠진 항목을 확인한다.

기존 표현의 해석은 그대로 보존한다

유해물질 “있음 / 없음 / 모름”은 유지한다. “없음”은 사용자 진술이고 분석 검증이 아니다. “오염 안 보임”은 눈에 보이는
오염이 없다는 뜻으로만 저장한다. 액체에 녹아 있는 성분·유분까지 없다고 해석하지 않는다.

혼합 체크는 간단하게 유지하되, 뒤에서 “서로 떨어지는 물건이 섞인 것인지, 코팅·접착 등으로 붙어 있는 재료인지”를 필
요할 때 묻는다. 이 구분이 분리·전처리 검토에 도움이 된다.

측정량과 발생 주기는 서로 다른 정보다

이번 처리량 200kg은 quantity.scope=current_lot으로 저장한다. 월 발생량 1t은 generation.amount=1, unit=t,
period=month라는 별도 기록이다. 두 값이 다르다는 이유만으로 충돌로 판단하지 않는다. 탱크 용량 100L, 포대 수 10개
를 실제 내용물 부피나 무게로 자동 변환하지 않는다.

기존 파트 1 명세에서 바꿀 내용

“대략적인 양”은 “실측·계수한 이번 처리량 또는 미확인”으로 바꾼다. 사진은 선택에서 폐기물별 전체·근접 최소 2장으
로, 담당자·사업자번호는 나중 수집에서 최초 수집으로 맞춘다. 실제 사업자정보 대조는 문서 작성 전 별도 검증한다.

명세 예시의 quantity.period=month는 이번 처리량에서 제거하고 발생 주기로 옮긴다. 상태 4종을 모든 상황에 공통 사
용하던 방식도 값의 확인 수준·충돌·분류 후보·단계 준비 상태로 나누어야 한다.

LLM 호출을 줄이는 기준

기존 템플릿, 수량 계산, 필수칸 확인, 상태 전환은 코드로 처리한다. LLM은 비정형 문서의 의미 해석과 자연스러운 질문 작
성에 집중한다. 파일 해시+추출기 버전으로 추출 결과를 재사용하고 변경된 필드에 관련된 규칙만 재실행한다.

초기에는 벡터 DB, 다중 에이전트, 자율 웹 탐색을 필수로 두지 않는다. 소수 폐기물군의 검수된 분류표·질문 규칙·안내 카
드로 정확성을 확보한 뒤 적용 범위를 넓힌다.

추출과 판정을 분리한다

추출 결과는 {field_path, raw_value, normalized_candidate, evidence_ref, warnings}로만 받는다. LLM이
accepted 값, verified 상태, case_version을 직접 변경하지 못하게 한다. DB 반영은 서버 검증과 사용자 검토를 거친다.

서버 검증 예시

200kg → 수치 200 + 단위 kg. 0.2t → 200kg은 계산 규칙을 남긴다. L·m³→kg은 해당 물질·조건의 밀도 근거 없이는 금
지한다. 음수, 복수 단위 혼재, 단위 누락은 질문한다. 0은 미확인과 다르며 이번 처리할 건에 0을 적으면 확인한다.

분석값은 물질명·값·단위·시험법·검출한계·채취일·시료번호를 함께 보존한다. “불검출”을 0으로 바꾸지 않고
qualifier=not_detected로 저장한다. 함량과 용출농도, 건조 기준과 습윤 기준이 다르면 직접 비교하지 않는다.

손상·암호화·지원하지 않는 문서는 임시 접수를 유지하고 대체 PDF/이미지를 요청한다. 구조화 출력 실패는 제한 재시도
후 질문 상태로 종료한다. 문서 안의 명령문은 실행 지시가 아닌 자료로 취급한다.

법령상 분류 후보를 만드는 방법
이름이 같아도 발생 시설·공정·성분 조건에 따라 분류가 달라질 수 있다. 명칭 유사도만으로 분류번호 하나를 결정하지 않
는다. 파트 1의 법령 기능은 근거를 붙인 후보 좁히기다.

단계                  구현 규칙


1. 기존 신고자료 추출       분류번호·문서 날짜·발급기관·현장·품목을 읽는다. reported_code로 저장하며 현재 건의 검증된 코드
                    로 바로 복사하지 않는다.


2. 공식 분류 기준 관리      국가법령정보센터에서 시행규칙 별표 4 등 관련 원문을 확보한다. 지정폐기물 여부 관련 시행령·시행규칙
                    의 조건을 함께 관리한다. [S1,S2]


3. 후보 검색            동의어·발생 공정·재질로 검수된 분류 테이블을 검색한다. code, 공식명, 적용조건, 제외조건, 필요필드,
                    원문 위치를 반환한다.


4. 조건 평가            각 조건을 true / false / unknown으로 평가한다. 미확인은 false가 아니다. 이름만 부합하면 후보 상태,
                    반증이 확인되면 제외 사유를 기록한다.


5. 질문 선택            후보를 가르는 업종·사용 원료·발생 시설·성상·시험 항목 중 현재 없는 정보를 질문한다. 판정에 필요 없는
                    질문은 생성하지 않는다.


6. 출력               후보별 근거·충족/미충족/미확인 조건을 전달한다. 모호하거나 지원 범위를 벗어나면
                    selected_code=null, review_required=true로 보류한다.

Rule: rule_id, source_id, effective_from, effective_to,
      code, official_name, conditions[], exclusions[],
      required_fields[], source_locator, reviewed_by
RuleResult: rule_id, result(true/false/unknown), fact_refs[]

원문 PDF/HTML, 개정·시행일, 수집일, 해시를 저장한다. 사람이 조건표와 원문을 대조한 후 활성화한다. LLM이 생성한

완료 기준과 구현 순서
아래 수치는 운영 성능 주장이 아니라 출시 전 확인할 목표다. 공개·합성·동의받은 비식별 문서로 정답 세트를 만들고, 프

검증 사례                          통과 기준


예시만 남은 표 / 복사한 표               가짜 폐기물 건 생성 0건. 복사된 태그 때문에 다른 건이 덮어써지는 오류 0건.


200kg / 0.2t / 100L / 포대 10개   허용 변환만 수행. 밀도 없는 부피→질량 변환 0건. 원문·단위·범위 보존.

재업로드 / 중복 실행 / 동시 수정           중복 건·중복 발행 방지. 충돌 응답 후 사용자 수정 보존.

순서대로 구현할 작업 묶음

1. 계약 먼저: WasteCase·Fact·Evidence·InformationRequest·이벤트 스키마와 합성 사례 3개를 팀이 고정한다. 단
일 재질, 구성 미확인 혼합물, 유해성 근거 부족 액체를 포함한다.

2. 수직 기능 완성: 자체 DOCX 한 건을 읽어 저장→질문 1회→사용자 확인→JSON 발행→파트 2 입력까지 먼저 연결한
다. 이후 다중 폐기물·수정 이력을 붙인다.

3. 추출 확대: PDF·스캔·분석결과서와 표·체크박스 처리. 원문 위치를 확인하는 화면과 실패 복구를 함께 만든다.

4. 분류·안내: 시연할 폐기물군의 검수된 법령 조건표, 질문 규칙, 자료 안내 카드를 구현한다. 나머지는 근거 부족으로 보류
한다.

5. 통합 검증: 역방향 보완 요청, 버전 영향, 동시 수정, 권한을 확인한다. 필드 정확도·근거 위치 정확도·불필요 질문 수·건
당 처리시간·OCR/LLM 호출량을 함께 측정한다.
